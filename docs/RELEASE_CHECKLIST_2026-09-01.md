# 2026-09-01 本地版本发布清单

> 当前状态：本地可发布，尚未获得新的部署授权。本文件只规定发布顺序、验证门和回滚边界，不会触发部署。

## 1. 已确认的部署约束

- 常规更新使用 `gtn-release.service` 单实例重启，不把蓝绿/静默更新作为默认方案。
- 用户未指定强制更新时，先确认没有进行中对局；有对局则等待，直到对局数为0再重启。
- 用户明确要求“现在更新”或同等含义时，无视是否有对局，直接按重启流程更新。
- 不额外创建手动数据库备份；继续依赖既有每日自动备份。
- 本轮 AI 入口保持关闭，发布验收不要求 Phelren 可进入或通过真实推理测试。
- 故事内容契约变化会在首次启动时清空旧旅程、旧手动存档、协作队伍和故事进度，保留图鉴发现。这个内容重置是预期行为，代码回滚不会自动恢复已清除的数据。

## 2. 重启前总门

- [ ] 固定待发布代码版本，确认 `git status --short` 与工作区基线一致，没有文件意外消失。
- [ ] `python -m pytest -q`、Python编译、`node --check static/js/story.js` 与 `git diff --check` 全部通过。
- [ ] 核对 `CHANGELOG.txt` 的最新日期、静态资源版本与故事内容版本。
- [ ] 只读取正式服状态和 `/api/health/full`，确认数据库、Socket、锁、房间和正在处理的动作没有异常。
- [ ] 若未收到强制更新指令，确认 `room_count=0`、`active_room_count=0` 后才进入重启。
- [ ] 明确记录更新前代码版本，以便只回滚应用代码；不执行额外数据库备份。

## 3. 四批发布验收门

四批按依赖顺序验证。实际代码可在一次获授权的重启中上线，但任何一批失败都停止继续开放后续功能，并按该批回滚边界处理。

### 第一批：规则、卡牌内容与对局正确性

范围：P1规则修复、卡牌/天赋平衡、伤害预测、死亡后多段停止、1v1/2v2权威结算与回放一致性。

重启后验证：

- [ ] 首页、卡牌目录、娱乐1v1和娱乐2v2可进入。
- [ ] 木板等指向型装备的预测与实际目标一致。
- [ ] 生物致死后不再继续播放受伤动画、承受后续段数或触发受伤被动。
- [ ] `room_action_busy_count=0`，没有新增服务端异常或重复结算。

失败边界：立即关闭新对局入口或回滚应用代码；不改写已完成对局结果。

### 第二批：单人和双人协作故事

范围：共享内容契约、五角色目录、角色/难度解锁、3至7列地图、房间/卡牌素材、三阶段协作旅程、个人奖励、阶段双确认与成员进度事务。

重启后验证：

- [ ] 普通的花花可开始单人标准旅程，未完成角色显示统一未就绪提示。
- [ ] Staff/Admin可见协作入口，普通账号不可见且直接接口请求被拒绝。
- [ ] 双人组队、邀请码、共同难度、双方个人赐福、路线投票和战斗状态可同步。
- [ ] 花园、丛林、工厂名称和阶段进度一致；第三阶段最终确认后双方各记录一次通关。
- [ ] 内容版本重置后图鉴仍保留，旧旅程/存档/进度已按契约清空。

失败边界：关闭协作功能开关；若是单人故事阻断问题则关闭故事入口并回滚应用代码。已发生的契约重置不能靠代码回滚恢复。

### 第三批：公告、投票与运营后台

范围：公告图片、投票、未投提醒、隐藏进行中票数、Staff/Admin运营工作区、更新日志草稿与审计。

重启后验证：

- [ ] 公告图片和公告入口正常显示。
- [ ] 普通账号只能读取/投票，Staff/Admin才能创建、发布、结束和审计。
- [ ] 同选项重试幂等、改票冲突、截止前票数隐藏、截止后结果公开。
- [ ] 跨站写请求和缺少CSRF的管理写入继续被拒绝。

失败边界：关闭或暂停运营写入口，保留公开只读内容；必要时回滚应用代码。

### 第四批：排位、信誉、关联账号与赛季经济

范围：四个核心PvP模式、新赛季、花阶结算、不可观战天梯、信誉/举报、自动关联、申诉、新人权益、荆露和防刷。

重启后验证：

- [ ] 娱乐与天梯1v1/2v2分栏正确；游客、非官方模组和低信誉账号无法进入天梯。
- [ ] 天梯进行中不可观战；娱乐不显示或结算花阶分。
- [ ] 重置前花阶分保留只读归档；R1沿用旧赛季/总花阶与计分场次，时代切换不清零。
- [ ] 同一比赛重试不重复结算花阶、信誉或荆露；冲突重试被拒绝。
- [ ] 校园/机房共享网络单独不会确认关联；公开资料不暴露设备、网络或内部关联证据。
- [ ] 新人第10/20场边界、前三场天梯保护、重复对手衰减与60秒内投降无荆露符合更新日志。

失败边界：优先关闭天梯/相关写入功能，娱乐模式保持可用；出现重复经济结算时立即停止新对局并回滚应用代码。

## 4. 获授权后的单实例重启流程

1. 再次读取当前正式实例、代码版本、`room_count`、`active_room_count`、锁和动作忙碌状态。
2. 按第1节的授权规则决定等待或立即执行，不创建静默更新倒计时，不切蓝绿实例。
3. 将已验收代码更新到正式发布目录，确认环境文件只从服务器既有配置加载。
4. 执行 `systemctl restart gtn-release.service`。
5. 检查服务状态、`/api/healthz` 和仅限本机/管理员读取的 `/api/health/full`。
6. 依次完成第3节四批冒烟验证；观察错误日志、房间数、动作忙碌数和数据库状态。

## 5. 完成与回滚判定

发布完成必须同时满足：服务健康、数据库和Socket正常、新对局可建立、四批冒烟全绿、更新日志可见，并且没有持续动作繁忙或跨站误拒绝。

若失败，先停止受影响的新写入或入口，再回滚应用代码并重启同一服务。数据库新增表/列按向后兼容设计保留；不要删除表、不要还原整个数据库、不要清理每日备份。
