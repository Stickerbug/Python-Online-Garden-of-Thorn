# GTN 模组编辑器设计（P0 方案）

目标读者：参与模组编辑器开发的协作者。

## 1. 背景与结论

目标用户是"有逻辑思维、但没有编程基础"的玩家：他们能想清楚一张卡该怎么结算，
但不会写代码、也不想学一套语法。

结论：

- 载体是**独立网页应用**（沿用现有 GTN Mod Studio 仓库），游戏本体只保留导入/入口。
- 主形态是**三栏工作台 + 句子式效果行**，逻辑用可排序、可缩进的效果行表达。
- **不采用 Blockly / 节点图作为主界面**（现有 Blockly 实现移除，可先导出其中的参数元数据）。
- **本期（P0）不做"试打"**，只做静态校验；试打方案见第 7 节，留待 P2。

## 2. 依据：现有 20 个官方模组包的统计

对 `mods/*.gtnmod` 全量解析（352 张卡、931 次 op 使用、115 种 op）：

| 指标 | 数值 |
| --- | --- |
| 卡片总数 | 352 |
| 效果步骤 1–2 步 | 208 张 |
| 效果步骤 3–5 步 | 112 张 |
| 效果步骤 6 步以上 | 22 张 |
| 完全没有嵌套 | 298 / 352 |
| 前 10 个 op 覆盖的使用量 | 66.8% |
| 前 25 个 op 覆盖的使用量 | 83.9% |
| 只用前 25 个 op 就能完整表达的卡 | 218 / 352 |
| 只被 1 张卡使用的 op | 61 个 |

结论：绝大多数卡片是"填表 + 排几行句子"，拖拽式画布的认知成本大于收益；
而 op 集合仍在演化（长尾很长），所以编辑器必须**从运行时生成选项**，不能硬编码。

包结构（`.gtnmod` 是 zip）：

```text
mod.json
locales/{zh,en,fr,ja}.json
card-art/*.svg
```

卡牌资源字段目前只使用 `image` 与 `upgraded_image`，**没有音频**，编辑器不做音频槽位。

## 3. 唯一契约：op schema

编辑器与游戏之间只靠一份机器可读的 op 定义对齐。

- 位置：`docs/mod-spec/op-schema.json`（放在游戏仓库，因为运行时在这里，"以代码为准"）。
- 生成：`tools/` 下的脚本扫描 `mod_runtime_v2.py`、`atomic_registry.py` 等注册表生成。
- 防漂移：加一条测试，断言"运行时已注册的 op 必须出现在 schema 中"，否则测试失败。
- 编辑器侧：构建时内置一份用于离线；启动时请求 `GET /api/mod-studio/schema` 拉最新，
  版本号不一致时提示用户（不强制阻断）。

每条 op 记录的字段：

```json
{
  "op": "deal_damage",
  "category": "damage",
  "params": [
    {"name": "target", "type": "target", "required": true},
    {"name": "amount", "type": "expression", "default": 0},
    {"name": "damage_type", "type": "enum", "options": ["physical", "magic"]}
  ],
  "events": ["on_play", "on_hit"],
  "label_zh": "造成伤害",
  "help_zh": "对选中的目标造成指定数值的伤害。",
  "example": "对 [选中的目标] 造成 [3] 点 [物理] 伤害",
  "deprecated": false
}
```

这份 schema 决定：效果行的可用句型、参数控件类型、默认值、人话报错、模板库内容。

## 4. 界面结构（三栏）

**左栏 · 资源树**：卡片 / 状态 / 标签 / 开局事件 / UI 组件；支持直接导入现有 `.gtnmod`。

**中栏 · 编辑区**：

1. 属性表单：费用、类型、品质、数量、标签、美术。
2. 效果行：每行是一句可读的话，行内下拉/数字控件，支持拖拽排序。

```text
对 [选中的目标] 造成 [3] 点 [物理] 伤害
如果 [目标] 已装备武器 → 对 [目标] 附加 [流血] [2] 层
对每个 [己方弃牌堆] 中的卡 → 随机置于 [自己抽牌堆顶]
```

条件与循环不用画布表达，用**缩进子行**表达，层级最多 2 层（现有数据里超过 2 层的只有 6 张卡）。

3. 描述联动：由效果行自动生成 `effect_text`，按 `docs/卡牌描述规范.md` 的四语言占位符规则输出，
   从机制上避免"描述和实现不一致"。

**右栏 · 预览与校验**：

- 卡面预览（四语言切换）。
- 静态校验结果：结构错误来自 `validate_mod_v2`，语义检查由编辑器补充，全部翻译成中文并定位到具体那一行。

## 5. P0 只加两个只读接口

```text
GET  /api/mod-studio/schema              # 返回 op schema 与版本号
POST /api/mod-studio/validate            # 提交 mod.json，返回 errors/warnings/语义检查
```

- 两个接口都**不执行任何模组逻辑**，只做数据校验，服务器成本可忽略。
- 体积上限 2 MB；按账号 + IP 限流；返回内容不包含服务器路径或堆栈。
- `validate` 先走 `validate_mod_v2`，再叠加语义检查（目标选择器与区域是否匹配、装备牌是否进入装备区、
  数值表达式是否恒为常量、描述占位符与四语言是否一致）。

**校验接口必须复用加载器的完整流程**，否则官方包会被误判成非法：

1. 先 `apply_mod_locales(data)` 合并 `locales/*.json`，再交给 `validate_mod_v2`（参考 `mod_loader.py` 的 `load_v2_mod_from_data`）；
2. 官方包走命名空间放行模式（`allow_reserved_namespaces=True`），社区投稿才用默认的社区模式
   —— 官方包的 `manifest.resource_namespace` 本来就可以与 `manifest.id` 不同（例如 `bio_dlc` 用 `bio` 命名空间）；
3. 直接调 `validate_mod_v2(data)` 会得到"未提供 locales/zh.json""命名空间不匹配"的假报错：
   实测 20 个官方包里有 7 个会被误判，20 个全部会被误报缺翻译。

## 6. P0 范围与验收

做：

- 资源树 + 属性表单 + 效果行（先支持前 25 个 op，覆盖 218/352 张卡的表达范围）
- 导入现有 `.gtnmod`、导出标准 `.gtnmod`
- 静态校验 + 人话报错
- 高频模式模板库、四语言填写与美术槽位

不做（留到 P1/P2）：

- 试打沙盒、`request_ui` 的 UI schema 编辑器、`event_hooks` / `patches`、社区发布、Blockly 进阶视图

验收标准：

1. 20 个官方包每个都能"导入 → 导出 → 再导入"，步骤数据语义无损（自动化用例）。
2. 用效果行搭出的卡，导出结果能通过 `validate_mod_v2`。
3. 每类校验错误都有中文提示并定位到具体行。
4. 只写中文、其他三语留空的包可以正常导出（回退链：目标语言 → default_language → en → zh）。

## 7. P2 试打方案（本期不实现，仅备案）

接口：`POST /api/mod-studio/test-play`，提交 mod.json，返回战报、运行时错误、关键数值。

实测成本（本地真引擎跑 352 张卡的环境）：

| 项目 | 数值 |
| --- | --- |
| 加载引擎 + 全部模组常驻内存 | 约 120 MB（峰值 146 MB） |
| 单卡 1v1 试打 | 平均 74 ms |
| 单卡 2v2 试打 | 约 0.13 s |

线上余量（2026-09-10 快照）：总内存 1608 MB，可用 619 MB，swap 4096 MB（已用 267 MB）；
游戏服务 cgroup 748 MB / 上限 1200 MB；2 vCPU。

必须满足的约束：

- 独立 systemd 单元，`MemoryMax` 约 400 MB，**不与游戏服务共用 cgroup**。
- 单并发队列，硬超时 5 秒，`RLIMIT_CPU` / `RLIMIT_AS`，超出直接 kill。
- 复用引擎步数预算；`request_ui` 自动选默认项，禁止挂起等待。
- 进程环境指向一次性 `GTN_DB_PATH`，绝不接触生产库；不写文件、不联网。
- 需要登录、按账号限流与每日配额、包体积上限；出问题有全局开关可一键关闭。
- 优先用"常驻父进程 + 每次 fork 子进程"的方式降低单次开销。
- 上线策略：先只对管理员开放，观察一周内存曲线后再放量。

## 8. 安全边界

- 社区模组只允许声明式 v2 DSL，禁止任意脚本；编辑器不执行用户代码。
- 资产白名单：svg/png，限制单文件大小与数量。
- 所有新增接口限流、限体积、错误信息不外泄。
- 试打（P2）与游戏服务在资源上完全隔离。

### 服务端接口（已实现，待部署）

`Python联机版/app.py` 里新增两个只读接口：

```text
GET  /api/mod-studio/schema      # 运行时全部逻辑 op、策展清单、引擎原子、未登记原子
POST /api/mod-studio/validate    # 只校验不执行；2 MB 上限；按 IP 限流
```

要点：

* `validate` 先 `apply_mod_locales()` 合并翻译，再用
  `validate_mod_v2(..., allow_reserved_namespaces=True)` —— 这两步缺一就会把官方包误判成非法；
* 两个接口都按 IP 限流（schema 60 次/5 分钟、validate 120 次/5 分钟），schema 带 5 分钟缓存头；
* 都不执行任何模组逻辑，服务器成本可忽略。

本地用 Flask test client 验证（未部署、未重启线上）：

| 请求 | 结果 |
| --- | --- |
| `GET /schema` | 200，ops 435 / coreOps 374 / unregisteredAtoms 61 |
| `POST /validate`（合法草案） | 200，`success: true`，errors 空 |
| `POST /validate`（`op` 写成 `not_a_real_op`） | 200，`success: false`，错误定位到 `registries.cards[0].events.on_play[0].op` |
| `POST /validate`（非 JSON 请求体） | 400 |

第三条正是"编辑器放行、线上报错"那类问题的拦截点。

### 性能实测与两道保险（2026-09-11）

用户的合理担心："部署在线服务会不会占真实游戏性能"。实测（Flask test client，本机）：

| 请求 | 耗时 | 备注 |
| --- | ---: | --- |
| `GET /schema` | **0.71 ms** | 响应 21 KB，带 5 分钟缓存头 |
| `POST /validate` 真实包（57 KB，Vanilla） | 5.7～8.3 ms | 冷启动首次 34 ms（线程内惰性 import） |
| `POST /validate` 合成 **478 KB / 416 卡** | **101～128 ms** | 逼近上限的最坏值 |
| `POST /validate` 超上限（513 KB） | 11 ms | 413 直接拒绝，不进校验器 |

**内存零新增**：`mod_validator_v2` / `mod_loader` / `mod_spec_v2` 在应用启动时已加载
（加载官方包用的就是它们），接口只调用既有代码，不连数据库、不执行引擎。

真正的风险是 **CPU 阻塞**：校验是同步工作，而 eventlet 是单线程协作式调度，
一段 CPU 密集代码会卡住同一 worker 上正在进行的对局通信。最坏约 130 ms（上限负载）。

两道保险（已实施）：

1. **上限降到 128 KB**（先定 512 KB，后按实测收紧）—— 官方包 `mod.json`
   最大 94 KB（Void Cards DLC，含缩进的原始文件）／73.5 KB（紧凑序列化），
   **20/20 个官方包全部通过**，余量 1.36～1.7 倍；最坏耗时从约 130 ms 降到约 30 ms。
2. **`eventlet.tpool.execute()` 把校验丢进线程池** —— 不再阻塞事件循环，
   与 `/api/community-mods/font-subset` 的做法一致（代码库既有模式，非新引入）。

限流仍在（schema 60 次/5 分钟、validate 120 次/5 分钟，按 IP）。

超限请求的代价几乎为零：实测 147 KB / 219 KB 的负载都在 **2～3 ms** 内返回 413，
不会进入校验器。若将来社区模组普遍超过 128 KB，改接口里那一行常量即可。

**另一处发现**：应用全局已设 `app.config['MAX_CONTENT_LENGTH'] = 1 MB`，
所以任何接口的实际请求体上限本来就是 1 MB；接口内的 128 KB 是更严的一道闸。

编辑器侧也接好了：线框图的"校验"区新增服务器地址输入框与「在线校验」按钮，
`buildDraft()` 把当前卡打成 v2 草案（含 `effect_text_i18n`、`events`），
POST 到 `<服务器>/api/mod-studio/validate`，把返回的 errors/warnings
直接渲染进校验面板（错误→红、警告→黄、通过→绿）。

**待验证**：这条链路的端到端联调被 `game_engine.py` 的语法错误挡住了——
2026-09-11 00:16 的改动让第 19391 行多了一层缩进
（`self.log_msg(...)` 应为 8 空格，实际是 12 空格），`import app` 直接失败。
之前用 Flask test client 验证两个接口时该文件还是好的，所以接口本身没问题，
是这之后的编辑引入的。修掉后即可联调。

**联调结果（语法错误修复后）**：

| 检查 | 结果 |
| --- | --- |
| `python app.py` 本地起服务 | ✅ 127.0.0.1:5000 |
| `GET /api/mod-studio/schema`（真实 HTTP） | ✅ 200，ops 436 |
| `POST /api/mod-studio/validate`（合法草案） | ✅ 200，`success: true`，errors 空 |
| 编辑器点"在线校验" | ❌ `Failed to fetch` —— **跨源被浏览器拦下** |

最后一条是真实拦截而非连接失败：响应里没有 `Access-Control-Allow-Origin`，
而编辑器与游戏服务不同源（例如 127.0.0.1:5145 → 127.0.0.1:5000）。

两种解法：

1. **编辑器侧代理**（推荐）：开发时用 Vite 的 `server.proxy` 把 `/api/mod-studio/*`
   转发到游戏服务；部署时由编辑器自己的后端代理。游戏服务的暴露面完全不变。
2. 游戏服务加 CORS 白名单：只对 `/api/mod-studio/*` 返回
   `Access-Control-Allow-Origin`（按 Origin 精确匹配 + `Vary: Origin`），
   不要用 `*`。

**已采用方案 1 并验证通过**：`vite.config.js` 里加了

```js
proxy: { '/api/mod-studio': { target: 'http://127.0.0.1:5000', changeOrigin: true } }
```

线框图的服务器地址输入框默认留空 = 走同源代理。实测（Vite dev server 3101 +
`python app.py` 5000）：点「在线校验」返回 **`服务器校验通过`**（绿色），
跨源拦截消失，且游戏服务不需要任何 CORS 配置。

### 四语言名称与美术槽位

属性区补齐了四个语言的名称输入框（中/英/日/法），改动直接写回该语言的
本地化数据，并随 `name_i18n` 一起发给预览宿主页。实测：

```
载入"重构机" → 中:重构机 / 英:Assembler / 日:再構成機械 / 法:machine de reconstruction
把日文改成"テスト名" → 切到日文页签 → 卡面显示"テスト名"
```

美术槽位：文件选择 + 缩略图 + 清除按钮；选中的图片读成 data URL 存进卡数据，
经 `def.assets.image` 交给游戏渲染器（iframe 与编辑器不同文档，本地路径取不到，
必须用 data URL）。**已验证的部分**：槽位渲染、未设置时的占位提示、
`renderPreview` 时会带上 `assets.image`；**未验证**：真实选文件这条交互路径
（Playwright CLI 的 `upload` 需要文件选择器弹窗状态，脚本化没跑通，
需要手动在浏览器里点一次确认）。

**已补验证（2026-09-11）**：用 `DataTransfer` 直接给 file input 塞文件绕开弹窗，
上传 `fire.svg` 后：

### 卡面预览：直接复用游戏自己的渲染

游戏卡面是纯 CSS + DOM 渲染的（`static/js/game.js` 的 `createCardElement()`，
`static/css/style.css` 里的 `.card` 一族选择器），不是贴图。所以编辑器不必重画卡面：

已经落地的做法（线框图里就是这套）：

* `tools/extract_card_css.py` 从游戏 `static/css/style.css` 抽出 487 条 `.card` 相关规则
  （含 `@media` 包裹的）和 `:root` 变量，生成编辑器侧的 `prototype/game-card.css`；
* 预览的 DOM 结构与 `createCardElement()` 一致：
  `.card.{thorn|bloom|root|guard}` → `.card-costs`（`.cost-e` / `.card-name` / `.cost-m`）
  → `.card-english-name` → `.card-art` → `.card-type-label-wrap` → `.card-effect`
  → `.card-bottom-zone > .card-flags > .card-flag.{cls}`（标签）；
* 类型颜色直接用游戏的 `var(--thorn)` / `var(--bloom)` / `var(--root)` / `var(--guard)`，
  卡框走 `--card-frame-color`，尺寸走 `--card-w`；
* 实测结果：190px 宽的预览卡渲染为 190×265、`aspect-ratio: 63/88`、
  圆角 `5.5% / 4%`、名字颜色 `#1ABC9C`，与游戏一致。

字体是最容易漏的一项：卡面文字继承游戏 `html, body` 的 `--font-main`，
而 `html.fonts-loaded-main` 会在字体加载完成后把它切成 Kreadon；
卡名另有 `--font-card`（Kreadon Demi + Kreadon CJK）。所以抽取脚本必须同时带上
`@font-face`、`:root`、`html.fonts-loaded-main`、`[data-theme="dark"]` 这些块，
并把 `url('/fonts/...')` 改写成编辑器内的相对路径，否则会出现"结构对、字体不对"。

标签（`.card-flag`）的类名与中文文案取自游戏：`CARD_FLAG_STYLES` 的 `cls`
加 `UI.flag_*`；带数值的标签（迅捷/沉重/电荷/副本/威力）渲染成 `标签: 数值`。

### 条件表达式的可视化编辑（已实现，覆盖两种常见形态）

效果行编辑器里的条件槽不再只读，`conditionEditor()` 会识别两类条件并给出结构化控件：

| 条件形态 | 可编辑项 | 其余部分 |
| --- | --- | --- |
| `compare{a, operator, b}` | 运算符下拉（≥ ≤ ＞ ＜ = ≠）、右侧字面量输入框 | 左值表达式只读显示（编辑左值需要更完整的表达式编辑器） |
| `not{value: card_has_tag{tag}}` | 标签下拉（显示中文名，如"放逐"） | — |

其他形态保持只读并提示"可在高级画布中修改"，避免破坏表达式树；
改动直接写回 `step.condition` 对象，走与槽位编辑同一条 `emit()` 路径。

实测（`jungle:magic_peas`，含两个 `if`）：4 行效果、**2 个结构化条件编辑器**渲染成功，
控件形如 `[上次受到的伤害] [＞ ▾] [0]`；未识别的形态按只读槽显示。

### 条件编辑与分支展开（三项补完）

1. **`and` / `or` 组合编辑**：条件树按 `compare` / `not+card_has_tag` / `and_or` 递归渲染，
   `and_or` 节点显示 `[左条件] [且/或 ▾] [右条件]`，可切换逻辑运算符。
   写回验证：把运算符从 `>` 改成 `<=` 后，`getSteps()` 回传的 JSON 里确实出现 `<=`。
2. **分支体展开**：`steps.js` 新增 `CHILD_KEYS`，把 `if.then/else`、`for_each.body/steps`、
   `once_per_play.steps` 展开成缩进子行，并带"则 / 否则 / 循环体 / 其中"的分支标签；
   子行的删除落到所属分支数组（`row.parentArray`），不会误删顶层步骤。
   实测 `jungle:magic_peas`：效果行由 4 行变为 **6 行（含 2 个子行，标签"则"）**。
3. **左值表达式结构化编辑**：`compare.a` 支持在下拉里切换形态
   （上次受到的伤害 / 目标状态层数 / 手牌数 / 抽牌堆数 / 目标属性 / 固定数值），
   并附带对应参数下拉（状态、属性）。写回验证：切成 `status_stack` 后 JSON 里出现该节点。
   不在列表里的复杂左值保持只读。

这批正是原子重构要消掉的长尾。

结论：**现在还不能摘掉 Blockly**。补 10 个左右通用句型（定时效果、自动打出、循环、
强制结束回合、清除/移除状态、UI 请求等）预计能把覆盖率推到 85% 以上；
剩下的大头会随原子重构自然收敛。

**第三批句型补完后**（`for_each`、`timed_effect`、`auto_play_card`、`queue_auto_play`、
`force_end_turn`、`draw_to_hand_limit`、`random_zone_card_to_hand`、`clear_status`、
`remove_status`、`request_ui`、`for_each_list`、`copy_card`、`spend_resource`、
`apply_burn`、`poison`、`apply_turn_regen` 共 16 个）：

| 指标 | 补之前 | 补之后 |
| --- | ---: | ---: |
| 句型模板覆盖的 op | 41 | **57** |
| 完全可表达的卡 | 235（68.3%） | **257（74.7%）** |
| 有障碍的卡 | 109 | **87** |

剩下的障碍已经退化成"每个 op 只挡 1–2 张卡"的长尾，而且前几名全是卡专用原子
（`ricochet_attack`、`honey_control`、`arctic_nuke`、`arctic_ruby_fuse`、`void_dlc_action`…）——
**这批只能靠原子重构消掉，不是编辑器该"补句型"的对象**。
换句话说：编辑器侧的通用句型已经接近饱和，接下来提升覆盖率的主力是重构本身。

### 把覆盖率当作重构的验收指标

`tools/editor_coverage_report.py` 现在会写基线并做差异对比，输出形如：

```
完全可表达：257/344（74.7%），上次 250/344（72.7%），变化 +7 张
新出现的障碍 op：honey_control×2
已消除的障碍 op：timed_effect×5
新变得可编辑的卡：1 张（如 arctic:snowflake）
```

基线文件：`模组编辑器/src/generated/editor-coverage.json`（记录每张有障碍的卡及其原因）。
`--no-save` 可只对比不更新基线。

用途：原子重构每推进一步就跑一次，用"还剩多少张卡在编辑器里改不动"作为**外部验收指标**——
比"还剩几个卡专用原子"更贴近实际影响面（一个原子可能只影响 1 张卡，也可能影响 20 张）。

### 卡面预览必须对齐的细节（踩过的坑）

| 项目 | 游戏行为 | 编辑器要注意 |
| --- | --- | --- |
| 类型标签 | `UI.card_type_*` 在四种语言下都是英文（Thorn / Bloom / Guard / Root） | 不要跟着界面语言翻译 |
| 卡片状态类 | `createCardElement()` 会加 `card-has-english` / `card-no-english` 与 `card-has-art` / `card-no-art` | `.card.card-has-art.card-no-english` 会改卡图与类型标签的外边距，漏加就会错位 |
| 费用圆圈粗细 | `border-width: var(--card-cost-border)` = `1cqi` | 浏览器会把 `border-width` **向下取整**：190px 卡上 1.9px 渲染成 1px。预览取 200/300/400px 这类整数比例尺寸才与游戏观感一致 |
| 卡名过长 | 中文名 ≥7 字时加 `card-name-long-zh`，字号从 10.5cqi 降到 8.9cqi | 长卡名预览要复现这条 |
| 效果文字 | 走 `colorizeCardText()`，关键词渲染成 `.card-token`、`[[icon:D]]` 渲染成内联图标 | 已移植：`tools/extract_card_text_rules.py` 抽出 77 条关键词规则、图标表与图标资源，编辑器用同一套规则着色 |
| 内联卡牌（`[[card:DefId]]`） | 走 `createCardChoiceChip()`，渲染成 `.choice-card-token > .choice-card-name`，颜色用卡牌类型色 | 已移植：卡名与类型从官方包索引（1037 条键）解析；卡面图不在 chip 内，不必抽资源 |
| 字体加载 | `html.fonts-loaded-main` 之后 `--font-main` 才切成 Kreadon；中文另有 1.16 MB 的 Kreadon CJK 子集 | 编辑器必须 `preload` 中文字体，否则首屏会先显示系统字体；`font-display: optional` 的 `Kreadon` 面加载超时会永久回退 |
| 每卡自适应 | 40 余个预设类（`card-nuke-compact`、`card-void-compact`、`card-assembler`…）按卡 id/名字表添加 | 未移植；这批类正是原子重构要清掉的对象 |
| 运行态 | `card-small` / `card-blinded*` / `card-disabled` / `card-draggable` / 动画类 | 静态预览不需要，做"实机尺寸预览"时要考虑 |
| 主题 | `[data-theme="dark"]` 的变量已抽取 | 预览默认浅色（游戏默认也是 light），可加开关 |

正式实现时的两个选择：

* 用一个 **iframe 沙箱**加载游戏的 `style.css` 与卡面字体（Kreadon），
  在 iframe 内构造与游戏相同 DOM 结构的卡面，实时更新；
* 好处是"所见即所得"——玩家在编辑器里看到的就是游戏里那张卡；
* 注意 `style.css` 有 470 KB 且与游戏页面耦合，必须放 iframe 里隔离，不要直接 import 进编辑器主页面；
* 卡图从模组包的 `card-art/*.svg` 读，字体与图标的路径按游戏版本固定，并记录版本号，
  游戏改版后要能提示"预览资源版本不一致"。

两条路线都成立：**抽取子集**（体积小、可控，但要记得游戏改版后重跑脚本）或
**iframe 直引整份样式**（零漂移，但要隔离）。当前线框图用的是第一条；
正式实现建议 iframe，抽取脚本继续用来做"版本漂移检测"。

### 可以模仿的对象

下表是建议照着抄的交互范式（来自已有产品的通行做法，具体站点可能已经改版，需要时我可以逐个打开确认）：

| 要解决的部分 | 参考产品 | 具体抄什么 |
| --- | --- | --- |
| 整体三栏 + 属性检查器 | Figma、VS Code | 左资源树、中编辑区、右检查器；分隔条拖拽；属性面板随选中对象切换 |
| 句子式步骤行 | Zapier、Make（原 Integromat） | 一步一张卡、一句话一行、行内下拉；"+" 插入新步骤；拖拽排序 |
| 条件分支的表达 | IFTTT、GitHub Actions 可视化编辑 | 条件行 + 缩进子行；不画连线 |
| 卡牌设计器（表单 + 实时卡面） | HearthCards、Card Conjurer、Magic Set Editor | 左表单右卡面的比例与排布；字段分组；字号/费用等数字字段的紧凑输入 |
| 长列表与筛选 | Linear、Notion | 352 张卡的列表用虚拟滚动 + 即时搜索 + 按类型/品质筛选 |

### 控件实现

下拉、可搜索选择器、数字输入、卡片选择器、分栏这些控件不必手写：
建议引入无框架的 Web Components 组件库（Shoelace / Web Awesome 一类，Vite 下直接可用），
配上现有 CSS 变量做主题覆盖；拖拽排序可以用 Pointer Events 自己写，或引入一个小型排序库。

### 主题策略

编辑器本体保持中性浅色（长时间编辑舒服），**卡面预览区用游戏真样式**（卡框、Kreadon 字体、
状态图标），形成"工具中性、成品还原"的对比。夜间模式不必在 P0 做。
