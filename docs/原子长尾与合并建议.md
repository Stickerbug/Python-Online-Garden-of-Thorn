# 原子长尾与合并建议（2026-09-11）

给接手清理原子的人：本文只讲**现状、口径、清单和建议顺序**，不含改法细节。
目标（用户原话）：**原子尽可能少，同时扩展性和功能尽可能丰富**。

## 一、统计口径（可复现）

三份数据来源：

1. `模组编辑器/src/generated/op-schema.json`（`tools/extract_op_schema.py` 生成）——编辑器与运行时的 op 契约；
2. `game_engine.py` / `mod_runtime_v2.py` 里 `def _atomic_<op>(...)` 的实现——处理器行数、读到的参数、
   是否直接委托给别的原子；
3. `mods/*.gtnmod`（20 个官方包）与仓库其余 `.py` 的引用计数。

复现思路：按 `def _atomic_<op>(` 切出函数体（切到下一个同级 `def`），统计行数、
`params.get('x')` 参数名、`self._atomic_y(` 委托；把处理器代码做"字符串/数字/属性名归一"后算
Jaccard 相似度找同形处理器；再递归扫包内 JSON 统计使用次数（步骤级与表达式级分开算）。

## 六、D 类：功能接近、但**每一个都很强**的原子（要小心合并）

这一类是"各自都有实现分量（≥25 行、多参数）、但解决同一类问题"的族群。
合并策略不是删，而是**抽出共同的"选择器/修饰器"，让动作参数化**。

## 七、让"原子少而强"的几条设计原则

1. **动词 + 选择器 + 修饰器**三段式：`for_each(选择器){ 动词 }`；伤害/受击/打出这类用修饰器
   挂载点（`on_hit`、`before_damage`、`on_failure`），不要为每个变体建 op。
2. **参数化，不要按对象建 op**：`apply_burn` 这种"动词固定 + 对象固定"是双重特化，
   应该变成 `status_add_named(status=…)`；同理区域、属性、资源都应走参数。
3. **选择器统一**：`target` / `zone` / `card_type` / `filter` / `count` / `mode` / `random` /
   `exclude_*` 这套参数在所有"选牌/选人"的 op 里保持一致（现在各写各的）。
4. **数据写法统一**：同一个动作不要有多个等价 op 名（`add_status`/`status_add_named`、
   `set_var`/`var_set`），编辑器和重构脚本只生成一种。
5. **契约自动生成 + 报告常态化**：白名单/参数从源码生成（已有
   `tools/extract_op_schema.py`），再加一个 `tools/op_long_tail_report.py`（形状相似度 + 使用计数 +
   白名单残留），每次改原子跑一次，长尾就不会再长回来。

## 八、建议顺序与验收

1. **删死重量（零风险）**：53 个卡组前缀 op + 8 个 `batch_*` + A 类别名指向的旧处理器；
   顺手把编辑器模板里唯一还在用的 `ocean_for_each_selectable_target` 改成 `for_each_target`。
2. **合并 C 类 6 族**（处理器骨架相同），并把数据写法统一（`add_status`→`status_add_named` 等）。
3. **按 D 类抽选择器/修饰器**：先做"区域批量操作"和"伤害"两族（使用量最大：126 + 31 次），
   它们决定编辑器模板的形状。
4. **验收口径**：`tools/editor_coverage_report.py` 的覆盖率不下降；白名单与有实现 op 数下降；
   官方 20 个包导入编辑器后 `错误 0 / 警告 0`；引擎测试全绿。
